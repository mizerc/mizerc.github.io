HTML Rendering Surface

Intro#

If one day you decide to create a graphics application, like a game or maybe a image editor; one of the first things you will need to create is a rendering surface. A surface that you can draw things over. Once we have access to that surface and a drawing API, we will be able to place vector geometrics such lines, rectangles, bezier curves; or rasterized pixels like filling a triangle, images and sprites.

This article will explore the journey of building a rendering surface using only the built-in features from the browser. And lets keep simple. No external libraries. No Godot, Unreal, p5.js, or Three.js.

Some features we want to support includes defining the canvas size to fill the browser window viewport, automatically resizing it when the browser window is resized, initializing the game loop, and rendering basic geometry using the 2D Context API.

History & Context#

In the 1990s it was common for games to use software rendering. Games like Quake I is a classic example. That time they lack the accessibility to hardware to help them to draw geometrics on the screen. They often had to use a single CPU, sometimes without extra cores and threads. So tey had to use clever algorithms to draw evertything: lines, triangles, images, polygons, mirros, shadows, scenes, heros and enemies…

With the advent of GPUs, shaders, and now AI, that kind of art has, of course, lost some of its value. So why write an article like this? I think part of the reason is that I want to visit that time by documenting the process and the pieces needed to recreate that kind of art. This is one of my favorites ways to learn; by understanding what is actually happening under the hood without the help of framework and libraries.

This will be the first and the simpliest: using HTML canvas to achieve that. In another future articles, I plan to explore other ways to building a surface using SDL2, glfw, AppKit, Win32, etc.

Analysins the HTML tags used#

Doctype#

The <!doctype html> is a way to tell the browser that we are opting in to use HTML5. The browser requires that explicitally because the internet has a lot of old websites using older version of HTML, and it could not assume that it would be ok using HTML5 everywhere since it would break things.

Encoding#

1

<meta charset="utf-8">

The encoding is necessary becase the HTML file is just a bunch of bytes that is sent by the server to your browser. And the browser needs to know how to map each byte, or sometimes a collection of bytes, into human readable characteres.

Normally the enconding used is returned by the server in the HTTP response headers as Content-Type. However, if that is not present, the browser will look for <meta charset ...> as a fallback. For example when the file itself is opened locally or served without that header.

The UTF-8 (U from Universal Character Set, TF from Transformation Format, 8-bit) is a character encoding standard capable of encoding all possible characters (called code points) in Unicode. It is also backward compatible with ASCII, covering all the 128 characteres. The encoding is variable-length and uses 8-bit code units. Common characters use 1 byte, and others use 2 to 4 bytes as needed.

Viewport#

1

<meta name="viewport" content="width=device-width, initial-scale=1">

The viewport is the entire space the browser will give to render the entire webpage. If we are building a rendering surface, often we want that the surface, aka Canvas, to fill that entire space. Later we will use CSS and JS to achieve that.

Importing external files#

1
2

<link rel="stylesheet" href="global.css">
<script src="main.js" defer></script>

As mentioned before, we will need to define a single CSS file and a single JavaScript file. We could write everything in this HTML file inside some special tags. But to keep things a bit more modular, lets import those files.

The defer attribute on <script> tag tells the browser to download the script in parallel while it keeps parsing the HTML, and run it only after parsing finishes. Without defer, the browser will hit that line and stop to parse the DOM until it is done parsing the script. The old workaround was to put scripts at the end of <body>.

Canvas#

1
2
3

<div id="gamecontainer">
    <canvas id="gamesurface"></canvas>
</div>

Here we define a container using a div. And we will use CSS to let the container to fill the entire viewport of the window. Later we will use JavaScript to get the current size of the container and resize the canvas to be exactly that.

The HTML <canvas> element, or just Canvas, is a powerful element. It can provide different rendering contexts, from 2D to advanced hardware accelerated. We will be using the 2D rendering context from the Canvas. But you can also get the WebGL for accessing the GPU thru OpenGL ES and writing shaders to render hardware accelerated 3D graphics. Modern browsers let you even access the webgpu context, which uses modern graphics standards like Vulkan, Metal, and D3D12. That offers better multithreading, lower CPU overhead, cleaner and safer API, etc.

Under the hood#

For 2d rendering, browsers like Chrome, uses Skia/Impeller under the hood. Which itself may use OpenGL, Vulkan, Metal or DirectX to talk with the GPU.

Removing spacing#

1
2
3
4
5

* {
    margin: 0;
    padding: 0;
    box-sizing: border-box;
}

The * selector selects all nodes (including nom rendering nodes, but this is a talk for another time).

Then we remove all margim and padding by setting them to zero.

Next we change the way the CSS engine parse sizes. The box-sizing: border-box makes the width and height of an element include its padding and border, making it easier to reason about the size of our layout. So if you set a div width to 100 pixels, then its border to 10px, the entire size of the div, including its border, will be 100 px. Without border-box, the size would be 100 px + 10 px of the border that would be added to it.

Defining the container size#

We want the surface to occupy the entire window viewport.

Using height: 100vh; for html and height: 100% for body and gamecontainer will tell the nodes around the canvas to fill the entire viewport of the window.

Finally, we can tell its child elements (body and gamecontainer) to take up 100% of their parent’s height by setting height: 100%.

All this will prepare the container around the Canvas element to fill the entire viewport space available in the current browser window. And if the user resize the browser window, everything will automatically resize together.

Layout size vs Resolution size#

Note that we didn’t define the canvas size using CSS. That size is also called “layout size”.

The strategy is that we want to let the CSS engine to define the layout size for us. Then, later, using JavaScript, we will read that value using canvas.clientWidth to define the canvas amount of pixels, aka resolution size.
